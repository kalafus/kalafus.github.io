Existing Apple Contacts cards have their own visibility. A native original containing that address stays readable until separately removed. The publication filter controls what Proto Contacts publishes; it does not redact independent cards or recall copies another app has saved.

1. Prepare only the chosen system view

ProjectionPolicy owns both contact selection and field filtering. The default policy selects all supported fields; contact and field selection narrow the published view. List membership remains outside the published fields. The provider encodes the already-filtered record. A selected contact with no publishable content produces no system item.

public func publicationResult(for contact: ContactRecord) throws -> ContactProjectionResult {
    guard contactSharing.includes(contact.id) else { return .omitted(.sharingSelection) }
    let allowed = effectiveFields
    let selected = contact.fields.filter { allowed.contains($0.key) }
    guard try selected.contains(where: { field, value in
        try field != .contactType && !Semantics.isEmpty(value, field: field)
    }) else { return .omitted(.noPublishedFields) }
    var projected = ContactRecord(id: contact.id, fields: selected,
                                  version: .init(), revisionID: contact.id)
    if case .scalar(.image(let photo)) = projected[.image] {
        // Public Contacts setters accept one image. Publish the rendered crop and retain the original in the vault.
        projected[.image] = .scalar(.image(.init(digest: photo.displayDigest)))
    }
    return .included(projected)
}

Proto Contacts can publish selected image crops, but cannot recreate the full-screen Poster designs. On the read-only iPhone/iPad route, the app prepares a separate projection database. The Contact Provider reads that database rather than opening the vault:

func contentDatabase() throws -> ProjectionDatabase {
    if let content { return content }
    guard let url = url() else { throw ContactProviderError.cannotEnumerate }
    let opened = try ProjectionDatabase(url: url, readOnly: true); content = opened; return opened
}

Source: Apps/ContactProvider/ProjectionEnumerator.swift, lines 13–17

The provider target links ProjectionKit and VaultCore; vault storage and key handling belong to the app. On iPhone/iPad, the provider route is used while a cloud Contacts account is enabled in system settings. When Contacts sync is disabled for every cloud account, the app can share through the editable on-device iPhone or iPad address book. Mac publishes into On My Mac where available. Both local routes apply the publication policy to app-owned copies; independent native records remain separate. See the setup guide for permissions, sharing enrollment, and account availability.

2. Encrypt storage and the cloud boundary

Local vault objects and cloud payloads use Apple CryptoKit’s XWingMLKEM768X25519_SHA256_AES_GCM_256 HPKE suite: hybrid ML-KEM-768/X25519 key establishment, HKDF-SHA256, and AES-256-GCM. Each object has a fresh encapsulation, with its record address authenticated as associated data. Contacts, photos, source snapshots, settings, history, and reset instructions use the same profile. There is no weaker fallback.

VaultCipher owns a versioned frame containing the encapsulation and authenticated ciphertext. Keychain holds the private-key seed; the key identity includes the encryption profile. Local and shared keys can differ, and the sync boundary re-encrypts between them. When sync is enabled, local storage keys are also backed up through synchronized Keychain for device-backup recovery. This storage protection is independent of the two selectable offline-backup layers.

public func encrypt(_ cleartext: Data, context: String) throws -> Data {
    var sender = try HPKE.Sender(recipientKey: key.publicKey, ciphersuite: Self.suite, info: Self.info)
    let encrypted = try sender.seal(cleartext, authenticating: Data(context.utf8))
    guard sender.encapsulatedKey.count == Self.encapsulatedKeySize else {
        throw VaultError.locked("The vault encryption provider returned an invalid encapsulation.")
    }
    return Self.header + sender.encapsulatedKey + encrypted
}

The upload path re-encrypts a locally stored object with the shared vault cipher and writes ciphertext into a CloudKit asset. The surrounding record carries metadata such as object kind and key identifier; it does not carry the key.

Key material is shared separately through iCloud Keychain. The resolver adopts the existing vault identity and waits if that key has not arrived. It does not substitute a new key for an established vault:

let keyID: String
if let existing = try await identity.loadKeyID() { keyID = existing }
else { keyID = try await identity.createIfMissing(keyID: local.keyID) }
try Task.checkCancellation()
if keyID == local.keyID { return .ready(local) }
guard let data = try await sharing.load(keyID: keyID) else { return .waiting(keyID: keyID) }
return .ready(try VaultCipher(keyData: data, expectedKeyID: keyID))

Source: Sources/ProtoContactsKit/VaultCloudKeys.swift, lines 67–73

ICloudVaultKeySharing connects that resolver to the synchronized Keychain implementation. The cryptographic operations and Keychain storage live in VaultCrypto.swift. Apple documents end-to-end encryption for Passwords and Keychain. This gives vault contents zero-access cloud encryption across upload, storage, and download, with decryption on the user’s devices. Cloud metadata and the deliberately readable system view have separate exposure.

3. Validate, record intent, then remove

Migration continues to import and reconcile source changes as the app runs and resumes. Removing eligible synced-account originals is an explicit account choice. The removal path checks the current source fingerprint, canonical record, and unresolved differences before accepting a validation receipt:

for snapshot in current {
    guard let mapping = try await repository.read(ExternalMapping.self, at: .init(.mapping, snapshot.key.storageID)),
          !mapping.isProjection, !mapping.sourceRemoved, mapping.originalRemovalPending == nil,
          mapping.latest.fingerprint == snapshot.fingerprint else { throw ReconciliationError.staleDifference }
    mappings.append(mapping)
    canonical.append(try await rawContact(validation.identities.canonicalID(mapping.canonicalID))
        .map(validation.groups.resolvingMemberships))
}

Source: Sources/ProtoContactsKit/OriginalRemoval.swift, lines 80–87

The shared removal helper commits that receipt and the exact pending source fingerprint before invoking the native save. A failed or uncertain save leaves recoverable intent; a later complete inventory reconciles the result before another removal attempt.

var receipts: [String: ValidationReceipt] = [:], prepared: [VaultWrite] = []
for (original, receipt) in originals {
    var mapping = original
    mapping.originalRemovalPending = mapping.latest.fingerprint
    receipts[receipt.id] = receipt
    prepared += try [VaultWrite(.mapping, id: mapping.id, value: mapping), VaultWrite(.receipt, id: receipt.id, value: receipt)]
}
try await repository.commit(prepared)
let removed = try await remove(receipts)

Source: Sources/ProtoContactsKit/OriginalRemoval.swift, lines 309–317

Editable iPhone/iPad sharing uses the same durable mechanism for duplicate cleanup. A retained native card must preserve the family’s information or an explicitly resolved scalar choice. Compatible partial cards can complete one existing keeper using only data already in that native family; vault-only fields stay out. The keeper is read back and verified before extras are removed. Unreadable fields block duplicate repair. Me Card protection, account choices, setup, and export/recovery pauses still apply.

See the keeper validation and consolidation paths and the user-facing cleanup guide. Removing originals, confirming sharing coverage, and counting extra native records are separate results.

Regression cases worth reading

  • Default publication and explicit filtering: field restrictions update the system copy while preserving the full vault record.
  • Compatible partial native cards: ordinary sharing retains one existing card, combines both native email values, and preserves vault-only data.
  • Interrupted native deletion: restart settles the saved removal scope without replaying the uncertain delete.

These tests use fictional records and controlled stores. They do not establish results on a real address book, account server, or second device. Proto Contacts remains a developer preview with no Proton service integration.
